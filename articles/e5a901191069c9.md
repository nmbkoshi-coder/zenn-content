## はじめに

AWSのセキュリティ運用を考える上で欠かせないサービスとして、Amazon GuardDutyとAWS Security Hubがあります。この2つのサービスは連携して動作し、脅威の検出から可視化までをカバーしています。

さらに2026年6月のAWS Summit New York 2026では、AIを活用した次世代セキュリティサービス「AWS Continuum」が発表されました。

本記事では、GuardDuty・Security Hub・AWS Continuumの3サービスの仕組みと関係性を整理しながら、AWSのセキュリティ運用がどのように進化しているかをまとめてみようと思います。

なお、AWSにはGuardDutyとSecurity Hub以外にもAmazon Inspector・Amazon Macie・AWS WAFなど多数のセキュリティサービスが存在しますが、本記事では「検出から集約・可視化までの従来フロー」を説明する上で最も代表的な2つのサービスに絞って解説します。

---

## 従来のAWSセキュリティ運用

### Amazon GuardDutyとは

Amazon GuardDutyは、AWSアカウント内の脅威を継続的に検出するマネージド型の脅威検出サービスです。エージェントのインストールや複雑な設定は不要で、有効化するだけで動作し始めます。

#### 検出の仕組み

GuardDutyは以下のログを分析し、機械学習と脅威インテリジェンスを組み合わせて脅威を検出します。

| 検出ソース | 内容 |
|-----------|------|
| AWS CloudTrail | AWSのAPI呼び出しの記録 |
| VPCフローログ | VPC内のネットワークトラフィック |
| DNSログ | DNSクエリの記録 |
| S3アクセスログ | S3バケットへのアクセス記録 |
| EKS監査ログ | Kubernetesの操作記録 |
| RDSログ | データベースへのアクセス記録 |

#### 検出できる脅威の例

- 不審なAPIコールや通常と異なるリージョンからのアクセス
- マルウェアに感染したEC2インスタンスによる不審な通信
- クレデンシャルの漏洩や不正利用
- S3バケットへの不審なアクセス

#### Findingsの重要度

GuardDutyが脅威を検出すると「Finding」として記録されます。重要度は以下の3段階で分類されます。

| 重要度 | 内容 |
|--------|------|
| HIGH | 即時対応が必要な深刻な脅威 |
| MEDIUM | 調査が必要な脅威 |
| LOW | 影響は限定的だが記録しておくべき事象 |

---

### AWS Security Hubとは

AWS Security Hubは、AWSアカウント全体のセキュリティ状態を一元的に可視化するサービスです。GuardDutyをはじめとする複数のAWSセキュリティサービスからFindingsを集約し、優先度付けや管理を行います。

#### Findingsの集約

Security Hubは以下のサービスからFindingsを自動的に集約します。

- Amazon GuardDuty
- Amazon Inspector
- Amazon Macie
- AWS Firewall Manager
- その他サードパーティ製品

#### セキュリティ標準への準拠チェック

Security Hubはセキュリティ標準に基づいた自動チェックを行い、準拠状況をスコアで可視化します。

| セキュリティ標準 | 内容 |
|----------------|------|
| AWS Foundational Security Best Practices | AWSが定めるセキュリティのベストプラクティス |
| CIS AWS Foundations Benchmark | CISが定めるAWSのセキュリティ基準 |
| PCI DSS | クレジットカード業界のセキュリティ基準 |

#### 複数アカウントの集約管理

AWS Organizationsと連携することで、組織内の全アカウントのFindingsを管理アカウントに集約して一元管理することができます。

---

### GuardDuty × Security Hubの連携

GuardDutyで検出されたFindingsはSecurity Hubに自動的に集約されます。これにより、GuardDutyの脅威検出結果をSecurity Hubの画面で一元的に確認・管理することができます。

#### 従来の対応フロー

```
① GuardDutyが脅威を検出（Finding生成）
        ↓
② Security HubにFindingsが自動集約
        ↓
③ セキュリティ担当者がFindingsを確認・優先度を判断
        ↓
④ 担当者が手動で対応・修復
```

#### 課題

このフローでは③④の工程が人手に依存しています。脅威の数が増えるほど対応が追いつかなくなるリスクがあり、対応速度にも限界があります。

## これからのAWSセキュリティ運用

### なぜAI-nativeなセキュリティが必要か

セキュリティの世界では、攻撃者もAIを活用する時代になっています。2026年4月7日、Anthropicは専門的なセキュリティモデル「[Claude Mythos Preview](https://www.anthropic.com/glasswing)」を発表しました。このモデルは最高レベルの人間のセキュリティ研究者に匹敵するレベルでソフトウェアの脆弱性を発見・悪用できる能力を持ちます。

Anthropicはその危険性を考慮してClaude Mythosを一般公開せず、代わりにAWS・Google・Microsoft・CrowdStrikeなどが参加する「Project Glasswing」という防御的イニシアチブを通じて、重要なコードベースの強化に活用しています。

[AWS Summit New York 2026の発表](https://aws.amazon.com/blogs/aws/top-announcements-of-the-aws-summit-in-new-york-2026/)の中でも、Claude Mythosのような特化型AIモデルの登場により、攻撃者・防御者双方が脆弱性の発見・悪用のスピードを大幅に加速させていることが言及されました。

つまり従来の「人が検出・判断・対応する」フローでは、攻撃の速度に追いつけなくなるリスクが高まっています。これが**防御側も機械の速度で対応する必要がある**という考え方につながり、AI-nativeなセキュリティサービスが求められる背景となっています。

---

### AWS Continuumとは

AWS Continuumは、2026年6月17日のAWS Summit New York 2026で発表されたAI-nativeなセキュリティサービスです。現在はコードの脆弱性を対象としたgated previewとして提供されています。

従来のGuardDuty + Security Hubが「検出・集約」を担い、その後の判断・対応を人が行っていたのに対し、AWS Continuumは**検出・優先付け・修復までをAIが自動的に実行**することを目指しています。

現在はgated preview（招待制のプレビュー）として、セキュリティ要件が複雑な金融サービス・自動車・テクノロジー分野の顧客と連携しながらプラットフォームを改善しています。

#### 主な機能

- 環境全体から脆弱性・リスクを継続的に検出
- ビジネスへの影響度に基づいた優先付け
- 実際に悪用可能かどうかの検証
- 既存のワークフローを通じた修復の自動化

#### Learn mode → Enforce modeの信頼モデル

AWS Continuumが特徴的なのは、AIへの信頼を段階的に高めていく設計になっている点です。

| モード | 内容 |
|--------|------|
| **Learn mode** | AIが検出・分析を行うが、実際の対応は人が判断する |
| **Enforce mode** | カテゴリごとに許可を与えることでAIが自律的に対応を実行する |

いきなり全ての対応をAIに任せるのではなく、カテゴリごとに段階的にAIへの委譲範囲を広げていける設計は、セキュリティ運用における信頼構築の観点で理にかなっていると感じます。

#### 今後の拡張

AWS Continuumは現在コードの脆弱性に特化していますが、将来的にはより広範なセキュリティ領域への拡張が計画されています。またモデル非依存の設計になっており、新しいモデルがリリースされ次第すぐに採用できる柔軟な仕組みになっています。

---

### AWS Security Agentとは

AWS Security AgentはAWS Continuumの一部として提供されているサービスで、開発プロセスにセキュリティを組み込むことを目的としています。

AWS DevOps Agentが「運用・障害対応」を担うのに対し、AWS Security Agentは「セキュリティの検出・修復」に特化したエージェントです。両者は役割が異なり、補完関係にあります。

#### 主な機能

| 機能 | 内容 |
|------|------|
| **脅威モデリング** | STRIDEフレームワーク※に基づいてアプリケーションの脅威を分析・可視化 |
| **PRコードスキャン** | GitHubなど主要なGitプラットフォームのPRを自動スキャンし修復を提案 |
| **IDE統合** | KiroやClaude Code pluginを通じて開発環境から直接セキュリティレビューが可能 |

※STRIDEとはMicrosoftが開発した脅威分類フレームワーク。なりすまし・改ざん・否認・情報漏洩・サービス拒否・権限昇格の6カテゴリで脅威を体系的に整理する手法。

開発者がコンテキストスイッチなしにセキュリティ対応できる点が特徴で、セキュリティを開発フローに自然に組み込む「Shift Left」の考え方と非常にマッチしています。

## 従来との比較

| 観点 | GuardDuty + Security Hub | AWS Continuum |
|------|--------------------------|---------------|
| 検出 | ✅ | ✅ |
| 集約・可視化 | ✅ | ✅ |
| 優先付け | ⚠️ 人が判断 | ✅ AIが自動判断 |
| 修復 | ❌ 人が対応 | ✅ 自動修復 |
| 対応速度 | 人の速度 | 機械の速度 |

---

## まとめ

GuardDuty・Security Hubは現在も非常に重要なサービスであり、AWSセキュリティ運用の基盤として広く使われています。一方でAWS Continuumの登場により、セキュリティ運用は「人が検出・判断・対応する」から「AIが機械の速度で自律的に対応する」方向へ大きく進化しようとしています。

AWS Continuumは現時点ではgated previewであり、コードの脆弱性を対象とした限定的な提供となっています。しかしLearn modeからEnforce modeへの段階的な信頼モデルは、AIへの委譲に慎重な組織でも導入しやすい設計だと感じます。

またAWS Security Agentの登場により、セキュリティは運用フローだけでなく開発フローにも組み込まれる方向に進んでいます。「作る段階からセキュリティを考える」というShift Leftの考え方が、AWSのサービス設計にも反映されてきていると言えるでしょう。

GuardDuty・Security Hubでセキュリティの基礎を押さえつつ、AWS Continuumの動向を追っていくことがAWSセキュリティ運用の今後の重要なポイントになりそうです。
